## 一、目标与范围

### 1.1 一句话目标

把"宿舍申请"从目前**只有一条入住申请直通**，补全为**入住 / 转移 / 退宿三类申请**从
"学生发起 → 辅导员审批 → 床位与宿舍数据即时生效 → 状态落库"的完整闭环，并支持**学生撤销**与
**辅导员查阅历史**。仍是单机文本存储、JavaFX 界面。

### 1.2 现状一句话

迭代一已跑通 `APPLY`（入住）一类：学生提交 → 辅导员通过并分配房间/床位或驳回。
`TRANSFER`（转移）/`EXIT`（退宿）在 `DormApplication` 中**只建模未启用**；无撤销；
迭代三全量种子数据里 **21,760 名学生已全部入住**，故"入住申请"在现数据下无法演示——
**本迭代真正可演示、也是重点的，是转移与退宿（以及退宿后再入住的闭环）**。

### 1.3 本期范围（Do）

- 三类申请的提交与校验（入住/转移/退宿）。
- 辅导员按类型差异化审批并**即时执行数据变更**（入住、换房、释放床位）。
- 新增状态"已撤销"，学生可撤销自己**待审批**的申请。
- 辅导员可查看本院**申请历史**（待审批/已通过/已驳回/已撤销）。
- 修复现状缺口（见 §三.3）：性别-楼栋匹配、一人至多一条待审批、审批前置状态校验等。

### 1.4 本期不做（Don't，后续扩展）

- **宿管科 / 宿舍管理人员的二级复核**（沿用已确认假设：先辅导员审批，复核留后续）。
- 跨学院转宿（目标楼栋不在本学院名下 → 需宿管科/目标学院介入，不做）。
- 退宿费用结算、钥匙/物品归还登记。
- 楼栋"按意愿/分数"排队分配（保持"辅导员人工选房"）。
- 换床（同房间内调床位，不单独建模；需求同转移，目标选同房即可，故不做单独类型）。

## 二、相关现状盘点（As-Is）

### 2.1 已具备的基础

| 部件 | 现状 | 位置 |
|------|------|------|
| 申请模型 | `DormApplication`：三类 `TYPE_APPLY/TRANSFER/EXIT`、三状态 `PENDING/APPROVED/REJECTED`、11 个字段 | `model/application/DormApplication.java` |
| 学生住宿 | `Student.currentBuilding/currentRoom`、`isCheckedIn()` | `model/Student.java` |
| 床位占用 | `Room.beds`（`Bed.occupantId`）、`findEmptyBed/isFull/availableBedCount/removeStudent/containsStudent` | `model/Room.java`、`model/Bed.java` |
| 楼栋-学院 | `College.buildingNames`；楼栋命名约定 `A栋=男 / B栋=女`（种子写死） | `model/College.java`、`storage/DataCenter.java` |
| 服务 | `DormApplicationService`：`submitApply/approve/reject/findPendingOfCollege/findApplicationsOfStudent` | `service/DormApplicationService.java` |
| 查询 | `DataCenter`：`findAvailableRooms(building)/findRoom(building,no)/findBuildingsOfCollege` 等 + 编号 `APxxxx` | `storage/DataCenter.java` |
| 学生端 UI | 菜单「宿舍申请 / 我的申请」两页 | `ui/StudentView.java` |
| 辅导员端 UI | 菜单「待审批申请」单页 | `ui/CounselorView.java` |
| 存储 | 每实体一个 `.txt`，`|` 分隔，`TextUtil.escape()` 转义，全量保存 | `util/TextUtil.java`、`storage/TextStorage.java` |

### 2.2 空床现状（演示可行性前提）

迭代三种子按 45 间/层 × 4 床/间排宿，楼栋容量取 `ceil(所需房间/45)` 层，**楼栋总有空床余量**：

- 理科学院：男 1,024 人 → A 栋容量 1,080（约 56 空床）；女 256 人 → B 栋容量 360（约 104 空床）。
- 文科学院相反（女多男少），结论相同——每栋都有空床。

→ 转移、退宿、再入住演示都有真实床位可操作，不必改种子。

### 2.3 现状缺口清单（本设计要修复）

1. **性别-楼栋不校验**：`submitApply` 只校验"目标楼栋属本院"，女生可选 `20A`(男) 栋；`approve` 同样信任前端选择。需在**提交与审批两处**都按性别收口（A 男 / B 女）。
2. **可重复提交**：同一学生可有多条待审批；无"一人至多一条"限制。
3. **无撤销**：误提交只能干等辅导员处理。
4. **已入住学生无可用流程**：界面隐藏申请区、service 拒绝 → 全量数据下 APPLY 永远进不来、TRANSFER/EXIT 尚未实现 → 学生端实际是"死"的。
5. **审批不校验当前状态**：`approve/reject` 未检查 `status==PENDING`，若界面数据陈旧重复操作会重复改库。
6. **退宿/转移无原宿舍快照**：通过后学生 `current*` 被改写/清空，历史记录追溯不到"从哪个宿舍来的"。
7. **辅导员无历史查看**：通过即从列表消失，审批留痕不可见。

## 三、申请类型与生命周期

### 3.1 类型定义（沿用现有常量，不新增类型）

| 类型 | 常量 | 中文 | 发起前置条件 | 通过时的数据变更 |
|------|------|------|--------------|------------------|
| 入住 | `TYPE_APPLY` | 入住申请 | **未入住**（已入住提示走转移） | 目标房间占一个空床，写 `currentBuilding/currentRoom` |
| 转移 | `TYPE_TRANSFER` | 转宿申请 | **已入住** | 释放原床位 → 新房间占一个空床 → 改写 `current*` |
| 退宿 | `TYPE_EXIT` | 退宿申请 | **已入住** | 释放原床位 → 清空 `currentBuilding/currentRoom`（学生仍在系统中，变"未入住"） |

> 目标楼栋：入住/转移需在提交时选择（**本学院名下且性别匹配**的一栋）；具体房间统一由**辅导员通过时**分配（延续现有交互）。退宿无目标楼栋。

### 3.2 状态机

```
                    学生提交
      ┌───────────────┼────────────────┐
      │ APPLY/TRANSFER/EXIT            │（新记录，编号 APxxxx）
      ▼                                │
   PENDING（待审批）                    │
      │  ▲                             │
      │  │ 学生撤销                     │ 学生撤销(仅 PENDING 可)
      │  └──────────────► CANCELLED（已撤销）
      │
      ├──辅导员通过并执行──► APPROVED（已通过·数据已生效）
      │       （APPLY:占床入住 / TRANSFER:换房 / EXIT:释放退宿）
      └──辅导员驳回──────► REJECTED（已驳回·无数据变更）
```

- `REJECTED` / `CANCELLED` 后可**再次提交**（新记录、新编号）。
- `APPROVED` 是终态，不改回；之后如需再调整，提交相反类型（如退宿后再入住）。
- **约束：同一学生任一时刻至多 1 条 PENDING**（任意类型），杜绝双流程冲突。

## 四、业务流程

### 4.1 入住申请（学生未入住 → 有床位）

```
学生(未入住) ──选择本院目标楼栋(A/B 依性别) + 原因──> PENDING
辅导员(本院) ──查看待审批──> 在目标楼栋内选有床房间
    ├─ 通过 → 占空床 + 写 student.current* → APPROVED
    └─ 驳回 → REJECTED
```
> 全量种子下学生均已入住，APPLY 主要出现在"退宿后再申请入住"等异常/补录场景。

### 4.2 转宿申请（学生已入住 → 换房）

```
学生(已入住) ──选择目标楼栋(本院/性别匹配) + 原因 ──> PENDING
辅导员 ──选目标房间 ── 通过时原子执行：
   1) 释放该生原房间床位（原房间即 student.current* 所在房）
   2) 新房间占一个空床
   3) 改写 student.currentBuilding/currentRoom → APPROVED
```
- 提交时**自动校验目标楼栋确实有空床**（空则提示辅导员无法分配）；通过时再以库内状态复核。

### 4.3 退宿申请（学生已入住 → 离开宿舍）

```
学生(已入住) ──原因──> PENDING
辅导员 ──通过(无需选房)──> 释放原床位 + 清空 student.current* → APPROVED（学生=未入住）
        └─ 驳回 → REJECTED（床位不动）
```
- 通过后该生可再走"入住申请"回住（演示闭环，见 §十一）。

## 五、业务规则与校验

> 校验分**提交时**与**审批时**两个时机；审批时以数据库最新状态**复核一遍**（防止界面陈旧数据）。

### 5.1 提交时（学生）

| 规则 | 说明 | 失败提示（示例） |
|------|------|------------------|
| 原因必填 | 三类都要，去空格非空 | "请填写申请原因" |
| 居住状态前置 | APPLY 需未入住；TRANSFER/EXIT 需已入住 | "您已入住，请使用转宿/退宿" / "您未入住，无法退宿" |
| 目标楼栋必选且属本院 | 入住/转移用 | "目标楼栋不属于本学院分配范围" |
| **性别-楼栋匹配** | A 栋=男、B 栋=女，须与学生性别一致 | "女生只能申请女生楼栋（B 栋）" |
| 目标楼栋有空床 | 入住/转移提交前预检一次（信息性，非强制放行） | "该楼栋暂无空床，请联系辅导员" |
| 一人至多一条 PENDING | 任意类型去重 | "您已有待审批申请，请等待处理或先撤销" |

### 5.2 审批时（辅导员，service 兜底复核）

| 规则 | 说明 |
|------|------|
| 状态须为 PENDING | 防止陈旧/重复操作 |
| 审批人须属申请人当前学院 | 沿用"按学院作用域"（见 markdown.md 审批假设） |
| APPLY：学生须仍未入住 | 复核 |
| TRANSFER/EXIT：学生须仍入住 | 复核；EXIT 通过会清空住宿，辅导员可见明确提示 |
| TRANSFER/APPLY 目标房间：在目标楼栋、属本院、性别匹配、有空床、不是自己现居房 | 逐条校 |
| EXIT：无需房间参数 | approve 忽略 room 参数 |

### 5.3 撤销

- 仅 `PENDING` 且操作人是申请人本人可撤销；置 `CANCELLED`，**无任何床位/数据变更**。

## 六、数据设计

### 6.1 DormApplication 字段（11 现有 + 2 建议新增）

| # | 字段 | 说明 | 变化 |
|---|------|------|------|
| 1 | id | 申请编号 `APxxxx` | 不变 |
| 2 | studentId | 申请人学号 | 不变 |
| 3 | type | `APPLY/TRANSFER/EXIT` | 不变 |
| 4 | targetBuilding | 目标楼栋（退宿为空） | 不变 |
| 5 | targetRoom | 审批分配的房号（通过后写） | 不变 |
| 6 | reason | 申请原因（自由文本，escape） | 不变 |
| 7 | status | `PENDING/APPROVED/REJECTED/CANCELLED` | **+CANCELLED** |
| 8 | createTime | 提交时间 | 不变 |
| 9 | reviewerId | 审批人（辅导员）id | 不变 |
| 10 | reviewTime | 审批时间 | 不变 |
| 11 | reviewComment | 审批意见 | 不变 |
| 12 | **originBuilding** | 提交时现居楼栋快照（转移/退宿用） | **新增（建议）** |
| 13 | **originRoom** | 提交时现居房间快照（转移/退宿用） | **新增（建议）** |

**为何加快照**：EXIT 通过后 `Student.current*` 被清空、TRANSFER 后被改写；若不留快照，
历史记录（辅导员历史页 / 学生我的申请）追不到"原宿舍"，报告过程记录不完整。
- 快照在**提交时**从该生当前宿舍写入；APPROVED 后保留。
- APPLY 原宿舍为空（未入住）→ 两列为空。
- 读取用 `TextUtil.safe` + `split("\\|", -1)`，对旧 11 列数据**向后兼容**（尾列取空串）。

**设计取舍（可调）**：若想少动模型与文件，可**不加**这两列，改为在展示时按
"申请人当前宿舍"推导；代价是追溯旧宿舍丢失。默认建议加。

### 6.2 常量与文案

- 新增状态常量：`STATUS_CANCELLED = "CANCELLED"`；`getStatusName()` 增 `"已撤销"`。
- 状态展示枚举：待审批(蓝) / 已通过(绿) / 已驳回(红) / 已撤销(灰)——颜色仅 UI 建议。

### 6.3 文件 dorm_applications.txt

表头（DataCenter.save 的 header 同步）更新为 13 字段，示例行：

```
# 宿舍申请表：id|studentId|type|targetBuilding|targetRoom|reason|status|createTime|reviewerId|reviewTime|reviewComment|originBuilding|originRoom
AP0001|25201101|TRANSFER|20B栋||和室友作息冲突，申请换宿|APPROVED|2026-09-02 10:00:00|25201|2026-09-02 10:30:00|已安排|20B栋|205
```

- `toLine()` / `fromLine()` 同步增列；其余自由文本照旧 `TextUtil.escape()`。
- `students.txt / rooms.txt / buildings.txt` **格式不变**（床位与当前宿舍即运行时数据）。

## 七、Service 层设计（`DormApplicationService`）

> 设计原则：**扩展为主**，沿用现有方法与命名习惯；规则收口 service，UI 只调方法。

### 7.1 方法清单（改动/新增以 ★ 标注）

```java
// ── 学生提交（新建 PENDING）──────────────────────────────
DormApplication submitApply(Student s, String targetBuilding, String reason);   // 改：性别/单待审批校验
DormApplication submitTransfer(Student s, String targetBuilding, String reason); // ★ 新增
DormApplication submitExit(Student s, String reason);                            // ★ 新增（无目标楼栋）

// ── 查询 ────────────────────────────────────────────────
List<DormApplication> findPendingOfCollege(String collegeCode);       // 沿用
List<DormApplication> findHistoryOfCollege(String collegeCode);       // ★ 新增：本院全部非 PENDING，按时间倒序
List<DormApplication> findApplicationsOfStudent(String studentId);    // 沿用

// ── 辅导员处理 ──────────────────────────────────────────
void approve(DormApplication app, Counselor c, String building, String roomNo, String comment); // 改：按类型执行
void reject(DormApplication app, Counselor c, String comment);        // 改：加状态复核

// ── 学生撤销 ────────────────────────────────────────────
void cancel(Student s, DormApplication app);                          // ★ 新增
```

### 7.2 关键实现要点

1. **提交统一入口收口**三个私有校验：`checkNotDupPending(studentId)`、`checkBuildingOfCollege(college,b)`、
   `checkGenderBuilding(student,b)`（A=男/B=女，可抽常量方法；名字含 `A栋` 尾为男）。
   创建记录时**为 TRANSFER/EXIT 写 origin 快照**；`dc.nextApplicationId()`、`saveAll()`。
2. **approve() 按 type 分支**（均先：状态 PENDING、审批人属申请人当前学院、居住前置复核）：
   - APPLY：校验目标楼栋性别/本院/空房 → 空床入住 → 写 current*。
   - TRANSFER：校验同上 + 目标非现居房 → **先 `Room.removeStudent` 释放原床位** → 新空床入住 → 写 current*。
   - EXIT：忽略 building/room 参数 → 释放原床位 → 清空 current*。
   - 收尾统一：`targetRoom`（EXIT 留空）、`reviewerId/reviewTime/reviewComment`、`status=APPROVED`、`saveAll()`。
3. **reject()**：加"状态 PENDING"与学院校验；无数据变更。
4. **cancel()**：校验是申请人本人 + PENDING → `status=CANCELLED`、`saveAll()`。
5. 床位释放/占用的原子性：所有变更在同一内存列表上完成，一次 `saveAll()` 全量落盘（现有架构本就如此）。

### 7.3 DataCenter 小改（建议）

- 可加便捷查询 `int availableBedCountOfBuilding(String building)`（遍历 `findRoomsOfBuilding` 累加），供
  学生提交页显示"该楼栋当前空床数"（可选，纯提示）。
- `saveAll()` 中 FILE_APPLICATIONS 的**表头文案**改为 13 字段（见 §6.3）。

## 八、界面设计（JavaFX，风格沿用现有视图）

### 8.1 学生端（`StudentView`）

**① 宿舍申请页（改造 `buildApply()`）** —— 单页内用类型选择控件（ComboBox：入住/转宿/退宿）切换表单：

| 区块 | 内容 | 交互 |
|------|------|------|
| 顶部说明 | 动态提示当前状态（未入住/已入住 于 20B栋-101） | 进入即加载 |
| 类型选择 | ComboBox，按居住状态**禁用非法项** | 切换即重排下方表单 |
| 入住 | 目标楼栋下拉（本院+性别匹配栋）+ 原因文本域 | 显示该栋空床数 |
| 转宿 | 显示现居宿舍 + 目标楼栋下拉（同上）+ 原因 | 目标默认过滤为"非现居、有空床"楼栋 |
| 退宿 | 显示现居宿舍 + **红字风险提示**（通过后床位释放、变未入住）+ 原因 | — |
| 提交按钮 | 提交对应类型 | 成功后清空表单、AlertUtil 提示、可顺手刷新"我的申请" |

- 若该生**已有待审批**：顶部黄字提示"您有 1 条待审批申请（类型：xx，编号：APxxxx）"，仍可查看但提交被拦（或提交按钮禁用）。

**② 我的申请页（改造 `buildApplications()`）**
- 状态**筛选下拉**：全部 / 待审批 / 已通过 / 已驳回 / 已撤销。
- 增列"原宿舍（originBuilding-originRoom）"（APPLY 为空），撤掉/保留"分配房间"列均可。
- **操作列**：对本人 `PENDING` 行显示「撤销」按钮 → 二次确认弹窗 → `service.cancel` → 刷新。
- 行展示按状态上色（可选）；表格控件与现有一致（`CONSTRAINED_RESIZE_POLICY`）。

### 8.2 辅导员端（`CounselorView`）

**① 审批页（改造 `build()`）** —— 保留"左侧待审批列表 + 右侧审批面板"：

- 列表列：编号 / 申请人 / 类型 / 目标楼栋 / 原宿舍 / 申请原因 / 提交时间（PENDING 列表）。
- 顶部加**范围筛选 ComboBox**：待审批 / 已通过 / 已驳回 / 已撤销 / 全部（即历史可查，见 ②，可不新增菜单项）。
- 选中一条后，右侧面板**按类型自适应**：
  - APPLY/TRANSFER：显示"目标楼栋 + 空床房间下拉"（沿用现有 `findAvailableRooms` 逻辑）。
  - EXIT：**隐藏房间下拉**，改为红字提示"通过后将释放该生床位并置为未入住"，「通过并退宿」按钮。

## 十一、验证与演示剧本（学院 20，软件学院·理）

演示账号：学生 `25201101`（女 · 20B栋）；辅导员 `counselor25201`（学院 20）。种子数据 20B 栋有空床。

| 剧本 | 操作 | 断言 |
|------|------|------|
| S1 退宿 | 25201101 登录 → 宿舍申请 → 退宿(原因) → 提交；counselor25201 登录 → 待审批 → 该条类型=退宿、无房选 → 通过 | 学生端"我的宿舍"变未入住；`dorm_applications.txt` 行状态 APPROVED + origin=20B栋|房间号；rooms.txt 原床位置空 |
| S2 再入住 | 同一学生 → 入住 → 选 20B 栋(只能选女栋) → 提交；辅导员通过并选 20B 栋空房 | 学生重新入住到所选房；床位占用一致 |
| S3 转移 | 该生 → 转宿 → 选 20B 栋 → 提交；辅导员通过并选**另一间**空房 | 原房床位释放、新房占床、current 更新、origin 记录原宿舍 |

## 十二、风险与已知限制（含后续扩展）

1. **性别-楼栋靠命名约定**（`A栋`男 / `B栋`女）写死。若未来给学院分配真实命名楼栋（如"天清苑"），
   该规则失效 → 后续建议给 `Building` 加 `gender` 字段（本期不引入）。
2. 辅导员作用域**按学院而非年级/专业**（现状）：所有本院待审批都会出现在任一本院辅导员列表。
   改按专业需动 `Counselor` 模型与 `findPendingOfCollege`（markdown.md 已记，本次不动）。
3. 通过即生效、无"两级审批"，**不可回滚**；错操作需反向流程修正（如误退宿→再入住）。
4. 全量种子"全部已入住"，APPLY 仅在退宿后再入住的场景出现——属预期，非缺陷。
5. 撤销只针对 PENDING；APPROVED/REJECTED 不可撤回（可后续加"撤销已通过并还原床位"，暂不做）。
