## 一、本次完成内容

### 1. 学生端（闭环发起方）

| 功能 | 发起 | 处理 | 数据变更 |
|------|------|------|----------|
| 购电 | 学生为**本人当前房间**提交购电（固定单价 0.60 元/度，显示预计金额） | 宿管科「售电」确认收费 | 购电单 PENDING→PAID；**房间电表余额** `Room.electricityBalance` 增加对应度数 |
| 维修报修 | 学生为本人当前房间填写维修内容 | 宿管科「修理管理」受理（PENDING→PROCESSING）→ 办结（→DONE） | 工单记录处理人 `handlerId` / 处理时间 `handleTime` |

学生端「我的宿舍」展示当前房间剩余电量；「购电 / 维修报修」两个新菜单页含表单 + 本人记录表。

### 2. 宿管科端（四大职责全部落地）

| 模块 | 内容 | 关键规则 |
|------|------|----------|
| 楼栋分配 | 楼栋 ↔ 学院分配/解除 | **已有学生入住的楼栋不可调归属**（须先腾空）；空楼可划拨/解除；每栋唯一归属，分配同步 `Building.collegeCode` + `College.buildingNames`。性别按 `Building.gender` 显式字段（缺省按 A栋=男 / B栋=女 推导） |
| 宿舍管理人员管理 | 增 / 改 / 删 / 查宿舍管理人员 | 可多选「负责楼栋」；删除前须先解除其负责楼栋；新增自动生成登录账号（用户名=工号小写，默认密码 123456） |
| 修理管理 | 全量维修工单按状态筛选处理 | 待处理→受理（处理中）→办结（已完成）；待处理也可「直接办结」 |
| 售电 | 待售电购电单确认收费 | 售电前显示房间当前电量，售电后房间电表到账、单据转「已售」 |

### 3. 宿舍管理人员端（三类日常登记全部落地）

| 模块 | 登记内容 | 校验 |
|------|----------|------|
| 夜归登记 | 学号 + 日期 + 夜归时间 + 原因 | 学生存在、已入住、且在**本人分管楼栋**内（service 收口） |
| 卫生检查 | 楼栋/房间 + 日期 + 得分(0~100) + 评语 | 房间属于分管楼栋；得分范围校验；记录 `inspectorId` |
| 贵重物品出入 | 学号 + 物品 + 方向（带出/带入） | 同上楼栋归属校验；自动记当前时间与 `handlerId` |

三类页面均为「表单 + 本人分管楼栋记录表」，登记前可查询学生/房间作预览确认。

## 三、关键设计决定

1. **闭环归属**：购电与报修是"学生发起→宿管科处理"，与角色职责表一致；宿舍管理人员只做日常登记，不处理修理工单/售电。
2. **楼栋性别显式化**：解决"真实楼名 + 性别"的楼栋分配需求（设计资料早已标注该方向）；既有 A/B 命名数据无需迁移即可继续用（`genderText()` 推导）。
3. **楼栋归属约束**：有学生入住的楼栋不可改归属，避免学生档案与楼栋归属矛盾；分配操作同时维护 `Building.collegeCode` 与 `College.buildingNames` 两处（`College` 列表继续承担"属于本学院分配范围"的校验）。
4. **新员工即开账号**：宿舍管理人员管理新增员工即生成登录账号，与 `accounts.txt` 的账号体系一致。
